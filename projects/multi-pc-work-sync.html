WORK SYNC BLUEPRINT

Multi-PC Work Sync

2대 이상의 PC에서 하나의 작업을 끊김 없이 부드럽게 이어가기 위한 최적의 상태 동기화 구조를 기술합니다.

기본 계층 4
권장 시작 Git + State
layers 권장 운영 구조

프로젝트의 소스 오브 트루스(Source of Truth)를 역할별로 격리하면 충돌 위험이 최소화됩니다.

LAYER 01

code Code Source

모든 소스 코드의 원본은 Git 원격 저장소입니다. 작업 시작 전 pull, 종료 시 push 원칙을 고수합니다.

LAYER 02

article Control State

project_control의 레지스트리와 상태 파일(states/*.md)이 현 작업 맥락과 다음 액션의 원본입니다.

LAYER 03

smart_toy Execution Auto

Harness 에이전트는 코드 무결성 검증, 신속 복구, 배포 전 체크리스트 실행 등 반복 작업을 자동 대행합니다.

LAYER 04

key Secrets & Runtime

비밀 키값(.env)이나 장비 의존형 환경은 개별 PC의 로컬 스토리지에 보존하며, Git이나 공용 문서엔 격리합니다.

autorenew 표준 작업 루프

동기화 누락이나 분기 혼선을 막기 위한 단계별 작업 흐름 규칙입니다.

01

Claim

시작 전 project_control을 가져오고(pull), 상태 파일에 작업 주체 PC와 분기 기준을 할당 기록합니다.

02

Work

기록된 계획을 바탕으로 작업을 전개하며, 추후 역추적이 용이하도록 작업 커밋 단위를 간소하게 분할 유지합니다.

03

Verify

로컬 구문 및 단위 빌드 테스트를 우선 수행하여 런타임 오류가 동기화 서버로 오염되지 않도록 단단히 체크합니다.

04

Handoff

작업 정지 시점의 코드 이력, 완료 작업, 잔여 테스크, 리스크 등을 상태 파일에 남겨 원격 저장소에 push합니다.

05

Resume

다른 PC에서 작업 재개 시 상태 파일을 먼저 검수하고, 기록된 형상 위치로 원복 후 개발을 이어나갑니다.

task_alt 운영 규칙

혼선 없는 동기화를 위해 반드시 준수하거나 지양해야 할 명확한 지침입니다.

check_circle 항상 지킬 것

  • 작업 착수 즉시 project_control과 핵심 소스 pull 하기
  • 중간 정지 시점마다 작은 단위의 커밋/기록을 원격에 동기화하기
  • 상태 파일에는 다음 담당자가 재개할 파일 경로와 행위 위주로 명시하기
  • 모든 검증 피드백을 상태 파일 이력이나 빌드 결과로 축적하기
  • 기밀 정보(API key, PW)는 전적으로 local .env 파일로 통제하기

cancel 피해야 할 것

  • 이전 이력을 확인하지 않고 무턱대고 로컬 소스만 덮어쓰기
  • 동기화 상태 갱신 없이 하루 이상의 업무를 로컬에 독점하기
  • 단일 브랜치를 무질서하게 동시 수정하여 과도한 conflict 유발하기
  • 작업 배포 및 성공 기록을 담당자의 단기 기억에 의존하기
  • 기밀 키나 암호화되지 않은 URL 정보를 공공 상태 문서에 기재하기

에이전트 제어 자동화 시스템(Harness)의 점진적 확장 기준입니다.

check_circle Git + State만으로 충분

  • 실 작업자가 1~2명 내외의 소수 인원일 때
  • 체크리스트의 검증 단계가 아직 복잡하지 않은 수동 중심일 때
  • 배포 빈도수가 극히 낮아 빌드/검증 파이프라인 자동화의 효용이 낮을 때

add_circle Harness 에이전트 도입 권장

  • 정밀 구문 점검, 정적 분석, 빌드 성공 여부를 완전 무인 자동화하고 싶을 때
  • 조직의 인원이 늘어나 코딩 컨벤션 및 배포 검증 규정을 강제해야 할 때
  • 여러 개발자의 동시 다발성 push 및 배포가 발생할 때
