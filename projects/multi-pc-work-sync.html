WORK SYNC BLUEPRINT

2대 이상 PC에서도 같은 작업을 끊기지 않게 이어가기 위한 운영 구조

`project_control`은 작업 문맥과 handoff를 관리하고, Git은 코드 기준점을 맞추며, Harness는 선택적으로 검증과 배포 자동화를 담당합니다. 핵심은 PC를 연결하는 것이 아니라 상태를 복구 가능하게 만드는 것입니다.

기본 계층 4
권장 시작 Git + State
권장 운영 구조

소스 오브 트루스를 계층별로 분리하면 PC 수가 늘어나도 운영이 덜 꼬입니다.

LAYER 01

Code Source

프로젝트 코드는 Git 저장소가 원본입니다. 모든 PC는 시작 전 `pull`, 종료 전 `commit/push`를 기준으로 맞춥니다.

LAYER 02

Control State

`project_control`의 `project_registry.md`와 `states/*.md`가 작업 문맥, 다음 작업, 리스크, handoff의 원본입니다.

LAYER 03

Execution Automation

Harness Agents는 코드리뷰, 검증, 배포 점검 같은 반복 작업을 자동화하는 선택 계층입니다.

LAYER 04

Secrets & Runtime

`.env`, 토큰, 로컬 런타임 정보는 PC별 로컬 보관 또는 비밀 저장소를 사용합니다. 상태 파일에는 넣지 않습니다.

표준 작업 루프

한 PC에서 끝낸 뒤 다른 PC가 바로 이어받을 수 있게 작업 루프를 고정합니다.

01

Claim

작업 시작 전 `project_control`과 대상 repo를 pull 하고, 상태 파일에 현재 담당 PC와 branch 기준점을 기록합니다.

02

Work

작업 중간에도 의미 있는 단위마다 commit 하며, 다음 PC가 이해할 수 있는 수준으로 변경 단위를 작게 유지합니다.

03

Verify

로컬 검증을 먼저 수행하고, 필요할 때만 Harness나 배포 파이프라인으로 확장 검증을 보냅니다.

04

Handoff

상태 파일에 완료 작업, 남은 작업, 다음 시작 위치, 리스크를 기록하고 push 합니다.

05

Resume

다른 PC는 상태 파일을 먼저 읽고, 마지막 branch와 commit 기준으로 복구한 뒤 바로 이어서 작업합니다.

운영 규칙

동시 작업 충돌을 줄이려면 몇 가지 규칙을 항상 지켜야 합니다.

항상 지킬 것

  • 작업 시작 전 `project_control`과 코드 저장소를 모두 최신화
  • 한 작업 단위마다 branch 또는 최소 commit 기준점 유지
  • 상태 파일에 다음 시작 위치를 코드 경로 단위로 기록
  • 검증 결과를 콘솔에만 두지 말고 상태 파일이나 CI 기록에 남기기
  • 비밀정보는 `.env` 또는 비밀 저장소로만 관리

피해야 할 것

  • 다른 PC에서 무엇을 했는지 모른 채 바로 수정 시작
  • 상태 파일 없이 긴 작업을 로컬에서만 진행
  • 여러 PC가 같은 branch를 장시간 무규칙하게 수정
  • 배포 검증 결과를 사람 기억에만 의존
  • 상태 파일에 토큰, URL secret, 계정정보 기록

Harness는 언제 붙이나

처음부터 무조건 붙이기보다, 반복 검증과 배포에서 이득이 생길 때 붙이는 편이 좋습니다.

먼저 `project_control + Git`로 충분한 경우

  • 작업자가 1~2명 수준이고 handoff 복구가 핵심일 때
  • 검증이 대부분 수동이거나 로컬 스크립트로 충분할 때
  • 배포 횟수가 적고 운영 정책이 단순할 때

Harness를 붙이면 좋은 경우

  • 코드리뷰, 오토픽스, 보안 점검, 배포 검증을 반복할 때
  • 실행 결과를 조직 정책과 승인 흐름 아래 두고 싶을 때
  • 여러 PC보다 여러 작업자가 동시에 검증/배포를 만질 때
